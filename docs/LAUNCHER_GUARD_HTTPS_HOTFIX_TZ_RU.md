## Проверенные позже факты (05–07.11) — важны для правильного диагноза

- **05.11:** на компьютере владельца публичный https://mag-mechanics-2.playit.plus/status через Playit выдавал HTTP 200 с заголовком Via: Caddy и версией Guard **0.2.1-local.3-admin.1**. Локальный Caddy на 127.0.0.1:443 (с именем хоста mag-mechanics-2.playit.plus) тоже отдавал 200. HTTP localhost:80 возвращал 308 на HTTPS. Порт 127.0.0.1:7454 отклонил соединение, но это само по себе не опровергает работу через Caddy. Проверена доступность GET /status из Польши, **не** успех POST /login или доступ из РФ.
- **Playit:** в консоли агента были control session expired и ConnectionReset (10054) управляющей сессии; нет доказательства, что они вызвали ошибку авторизации игроков.
- **07.11:** у **Ани из России** вход снова заработал. У **Нади из России** лаунчер продолжал жаловаться на SSL, голос Discord имел среднюю задержку 4509 мс и последнюю 5000 мс. Это противоречит гипотезе о блокировке для *всех* игроков РФ и допускает отдельную проблему её маршрута, провайдера, системы фильтрации или Zapret.
- **Надин Zapret:** диагностикой обнаружен запущенный winws, широкие правила TCP/UDP и DPI-desync. Отсутствует полный список применённых hostlist/ipset; **не доказано**, что именно Zapret обрывает HTTPS Guard. Первый архив MM2_Diagnostic_20261107_214508.zip был пустым; следующий диагностический отчёт был неполным. Не трактовать отсутствие логов как успешный тест. Discord без Zapret у Нади может быть недоступен: не предлагать отключение как универсальный тест голосового чата.
- **Старый репозиторий Zapret на GitHub** возвращал 404 также при внешней проверке; 404 сам по себе не доказывает сетевую блокировку.
- **Манифест:** подтверждённый исходный Release Asset player-mods-1.4.17.json содержит 108 файлов и Guard **0.2.1-local.2** с корректным SHA256. В старой диагностике Нади локально присутствовал **0.2.0**; нужно исследовать клиентскую синхронизацию, но этот JAR ранее сосуществовал с работавшим серверным Guard. **Разница версий сама по себе не является объяснением TLS reset.**
- **Лаунчер:** версия 1.4.21 у Нади **успешно авторизовалась 28.10**, 30.10 начала выдавать TLS reset, 1.4.22 не помогла. Коммиты публикации в GitHub меняли launcher-update.json, а не реальный код ActivationService. Нельзя по этим коммитам доказать, что именно клиентский бинарник ломал вход.
- Владелец ранее удалял старые каталоги, репозитории и возможно ресурс-пак. Связь с инцидентом остаётся гипотезой. Не подменять диагностику случайным откатом/заменой Guard.

**Если проблема вернётся:** собрать свежие журналы одного успешного и одного неуспешного клиента, отдельно проверить TLS/Playit/Guard POST /login без раскрытия учётных данных. Текущая очередь обновления модов — в новом ТЗ выше. Секреты, токены, email и полные личные архивы в публичный GitHub не добавлять.


**05.11.2026. Приоритет: быстрый точечный hotfix, НЕ переделка лаунчера/Guard.** Владелец предполагает, что одна из недавних правок Codex при удалении старых каталогов модов/репозиториев (около 30.10–01.11) могла нарушить вход. Это **гипотеза, не доказательство**. Найти конкретный сломанный шаг и исправить его; не растягивать задачу на полную переработку всех подсистем.

## Симптомы и ориентиры

- У владельца вход работает, у нескольких остальных игроков — нет. В архиве Нади `хэнк.zip` (если доступен в рабочей среде) ошибка `ActivationService.LoginAsync` → `HttpRequestException: The SSL connection could not be established` → `SocketException (10054)`, удалённый хост сбросил соединение. HTTPS `https://mag-mechanics-2.playit.plus/status` у неё не проходит, но игровой TCP-порт доступен. **Игровой TCP ≠ API авторизации**.
- 28.10 у Нади проходила авторизация с серверным Guard `0.2.1-local.3-admin.1`; 30.10 ошибка была уже на лаунчере 1.4.21, сохранилась на 1.4.22. Клиентский Guard у Нади `mag_mechanic_guard-0.2.0.jar`.
- В GitHub `player-mods.json` основной ветки указан клиентский Guard **0.2.0**. В релизе `launcher-1.4.17` лежит **0.2.1-local.2**; отдельный манифест `player-mods-1.4.17.json` нужно прочитать и проверить, что реально использует действующий лаунчер. Предыдущая успешная работа 0.2.0 с серверным 0.2.1-local.3-admin.1 означает, что **само несовпадение версий не доказало причину SSL-сбоя**.
- В админ-панели иногда отображается устаревшая версия лаунчера игрока, хотя фактически установлена 1.4.22. Это может быть независимой проблемой устаревшего статуса.
- Владелец удалил и старый репозиторий с ресурспаком; ссылка могла остаться. Проверить, но **404 ресурспака нельзя объявить причиной TLS-сброса без трассировки**.

## Новая проверенная находка 05.11 — JAR владельца и манифесты

Владелец передал `mag_mechanic_guard-0.2.1-local.2.jar`. Проверены SHA-256 `fa1c17753d63c10295bd9c4e146f8979b74ffaba45002b6d15c78b9be6325cff` и размер 56 406 байт: файл **уже опубликован** в GitHub Release `launcher-1.4.17`, повторно загружать не требуется. `neoforge.mods.toml` указывает версию `0.2.1-local.2`, side BOTH, NeoForge `[21.1.230,)`. Это файл владельца, **не подтверждённая установленная сборка рабочего сервера**.

**Статический анализ JAR (без запуска):** в моде используется `com.sun.net.httpserver.HttpServer` — **HTTP**, не встроенный HTTPS. Есть API-маршруты `/status`, `/login`, `/admin/status` и др. `LocalNetworkPolicy.bindAddress()`: по умолчанию режим `local` = `127.0.0.1`; системное свойство `magmechanic.guard.networkMode=external` меняет привязку на `0.0.0.0`. Проверить фактический port/bind, где завершает TLS Playit/прокси и как туннель обращается к локальному HTTP API. При необходимости проверить `apiPort=7454` в `config/mag_mechanic_guard/guard.properties` и его переопределения, а не предполагать, что порт верный. Не открывать API в интернет напрямую без проверенной модели защиты.

В GitHub **изменён только основной** `player-mods.json`: теперь он ссылается на уже опубликованный `0.2.1-local.2` по точной контрольной сумме, коммит `26a09cf`. **Проверено по скачанному оригинальному Release Asset `launcher-1.4.17/player-mods-1.4.17.json`** (SHA-256 самого JSON `ce4499962fbfcece0229fdcf42078f84b1538ca6c24f7e16e83bf66d673d5143`, размер 49224 байта). Манифест содержит 108 required-модов, NeoForge 21.1.248, **и Guard там УЖЕ `mag_mechanic_guard-0.2.1-local.2.jar`**, SHA-256 `fa1c17753d63c10295bd9c4e146f8979b74ffaba45002b6d15c78b9be6325cff`, размер 56406, правильный URL GitHub Release. **Ничего исправлять в закреплённом манифесте Guard не требуется; не перезаписывать релиз.** У Нади при этом в локальной диагностике был Guard 0.2.0: проверить, почему действующий лаунчер не обновил локальный мод, а не считать серверный манифест старым. Отдельно: **104 из 108 модов имеют резервный URL на `mag-mechanics-2.playit.plus`** — поломка HTTPS на этом хосте одновременно влияет на вход и fallback-загрузки, но не доказывает одну корневую причину. Основной `player-mods.json` после правки `26a09cf` также 0.2.1-local.2, но это другой, более старый по составу набор (86 модов); не смешивать каталоги. SSL/TLS reset авторизации отдельно от обновления модов.

## Сделай по порядку — сначала быстрое расследование последнего изменения

1. **Снимок текущего состояния без правок:** найти фактический запущенный серверный Guard JAR, SHA-256/версию, его `guard.properties`, процесс/порт API, Playit HTTPS-туннель, логи старта/ошибок, реальный exe лаунчера, используемый URL авторизации и манифест. Не считать исходники или имя файла доказательством запущенной версии. Не публиковать токены/пароли.
2. **Сравнить с последней рабочей конфигурацией 28.10:** посмотреть git diff, локальные изменения, историю действий Codex, удалённые папки, даты пересборки и развертывания Guard, обновления лаунчера и Playit. Найти минимальную перемену, способную разорвать связь. Если такой перемены нет — честно зафиксировать.
3. **Разделить HTTPS от логики Guard:** проверить локальный `/status` на сервере и тот же маршрут по публичному HTTPS (TLS/SNI/сертификат, проксирование, правильный внутренний порт, HTTP-ответ). Сравнить с запросом проблемного клиента; при TLS-сбросе до HTTP искать причину в сети/туннеле/клиентских фильтрах, при отказе локального API — в Guard. Не делать вывод по одному ping/TCP. У Нади есть Kaspersky, Radmin VPN, winws/Zapret: проверить сравнением через другую сеть, **не обвинять их без воспроизведения**.
4. **Проверить клиент/сервер Guard и обновления:** выяснить назначения 0.2.0, 0.2.1-local.2 и 0.2.1-local.3-admin.1; сравнить метаданные и код фактически доступных JAR, подтвердить используемый манифест, нет ли конфликта/двойной установки. У пользователя должен быть **один согласованный клиентский комплект**; админка открывается по серверной роли аккаунта, не требует отдельного несовместимого Guard. Не обновлять/удалять JAR вслепую.
5. Проверить ссылки на удалённые репозитории и ресурспак в настройках лаунчера, Guard, `server.properties`, манифестах и скриптах. Зафиксировать только реально вызываемые адреса и влияние ошибок на вход.
6. **Подготовить минимальный фикс** именно найденной причины в коде или конфигурации. Прогнать изолированные тесты: обычный пользователь — вход/выход/повторный вход; администратор — вход + панель; HTTPS статус/авторизация; синхронизация модов; обновление показанной версии клиента. Если один пункт не связан с основным сбоем, не блокировать им hotfix, записать как отдельную задачу.

## Границы и результат

- **Не менять рабочий сервер/Guard, аккаунты, мир, продакшен-манифесты или Playit без резервной копии и отдельного разрешения владельца.** Не отключать проверку TLS-сертификатов, не обходить авторизацию. Изолированные исправления в коде и тесты разрешены.
- Нужен **короткий отчёт**: сломанный компонент → доказательство (лог/URL/коммит/конфигурация) → исправленные файлы и commit → результаты входа обычного игрока и админа. Если доступ к рабочему серверу недоступен — перечислить **ровно какие данные нужны**, не объявлять задачу выполненной.
- **Не переписывать всю архитектуру** и не уходить в долгие исследования, если проблему можно устранить исправлением одной конфигурации или одной ошибочной правки. Но не объявлять исправление рабочим без проверки реального входа.
